# AI Lead Assistant

**AI Lead Assistant** — Telegram-бот для первичного приёма и структурирования заявок на разработку AI-решений. Бот ведёт диалог с потенциальным клиентом, извлекает сведения о проекте с помощью OpenAI, показывает заявку для подтверждения, сохраняет её в SQLite и уведомляет оператора в Telegram.

**Демонстрация:** [@glazounov_ai_leads_bot](https://t.me/glazounov_ai_leads_bot)

> MVP работает в Docker на постоянно включённом компьютере разработчика. Доступность бота зависит от работы компьютера, Docker, сети и Telegram; облачное размещение пока не реализовано.

## Возможности

- Диалог с клиентом на естественном языке через Telegram.
- Извлечение и накопление сведений о заявке с помощью OpenAI (модель по умолчанию `gpt-4o-mini`, задаётся через окружение).
- Сбор имени, контакта и бизнес-задачи; при наличии — компании, типа решения, интеграций, сроков и бюджета.
- Просмотр заявки перед отправкой и подтверждение через кнопки Telegram.
- Сохранение подтверждённой заявки в SQLite **до** отправки уведомления оператору.
- Уведомление оператора о новой заявке и отдельная фиксация статуса доставки.
- Операторские команды для просмотра, ручного подтверждения доставки, безопасного сброса застрявшей отправки и повторной отправки уведомлений.
- Одноразовые Telegram-кнопки подтверждения для `/reset_delivery` с привязкой к циклу доставки.
- Журналы `delivery_attempts` и `operator_actions`.
- Постоянное хранилище SQLite в Docker volume.
- Автоматические тесты основных компонентов и диагностический скрипт для безопасной проверки `/reset_delivery`.

## Как работает

1. Клиент открывает бота и отправляет `/start`.
2. Описывает задачу и отвечает на вопросы ассистента.
3. OpenAI помогает выделить структурированные данные заявки.
4. Бот показывает сводку с кнопками подтверждения или исправления.
5. После подтверждения заявка сохраняется в SQLite со статусом принятия.
6. Бот переводит доставку в `sending` и пытается отправить уведомление оператору.
7. Результат доставки (`sent` или `uncertain`) записывается отдельно от факта принятия заявки.

**Важно:** сбой отправки уведомления не отменяет уже принятую заявку. Повторно оформлять её клиенту не нужно.

## Архитектура

```text
Клиент в Telegram
       |
       v
Telegram Bot (python-telegram-bot)
       |
       +--> OpenAI --> извлечение полей заявки
       |
       +--> LeadWorkflow --> сводка и переходы состояния заявки
       |
       +--> SQLite
       |      sessions
       |      leads (+ delivery_cycle_id)
       |      delivery_attempts
       |      operator_actions
       |      delivery_reset_confirmations
       |
       +--> Telegram API --> уведомление оператору
                                  |
                                  +--> /leads, /lead, /pending
                                  +--> /retry, /mark_sent
                                  +--> /reset_delivery (+ callback)
```

## Настройка и запуск

### Требования

- Docker с поддержкой Docker Compose.
- Токен Telegram-бота, полученный через [@BotFather](https://t.me/BotFather).
- Ключ OpenAI API.
- Telegram user ID оператора для личного чата с ботом.

### 1. Подготовка окружения

Скопируйте `.env.example` в `.env` и заполните реальные значения:

```powershell
Copy-Item .env.example .env
```

Переменные окружения (см. `.env.example`):

| Переменная | Назначение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен бота |
| `TELEGRAM_OPERATOR_CHAT_ID` | Telegram user ID оператора (личный чат) |
| `OPENAI_API_KEY` | Ключ OpenAI API |
| `OPENAI_MODEL` | Модель OpenAI (по умолчанию `gpt-4o-mini`) |
| `OPENAI_BASE_URL` | Базовый URL API OpenAI |
| `DATABASE_PATH` | Путь к SQLite внутри контейнера/процесса (по умолчанию `data/sessions.db`) |

`compose.yaml` подключает `.env` через `env_file` и монтирует именованный volume `ai_lead_data` в `/app/data`.

**Никогда не публикуйте `.env` с действующими секретами.** Файл исключён через `.gitignore`.

### 2. Запуск

Из корня проекта:

```powershell
docker compose up -d --build
```

Проверка состояния:

```powershell
docker compose ps
```

После запуска откройте бота в Telegram и отправьте `/start`.

### 3. Остановка и перезапуск

```powershell
docker compose restart ai-lead-assistant
```

Для остановки:

```powershell
docker compose down
```

**Не используйте `docker compose down -v`, если хотите сохранить заявки:** эта команда удаляет именованные volumes проекта, включая SQLite.

## Команды Telegram

### Клиент

| Команда | Назначение | Ограничения |
|---|---|---|
| `/start` | Начать оформление заявки | Только личный чат |
| `/cancel` | Прервать текущий незавершённый диалог | Нельзя отменить заявку, уже находящуюся в обработке доставки |

### Оператор

Операторские команды доступны **только** пользователю из `TELEGRAM_OPERATOR_CHAT_ID` и только в **личном** чате с ботом. Идентификатор заявки — полный UUID.

| Команда | Назначение | Ограничения и последствия |
|---|---|---|
| `/leads` | Показать до 10 последних заявок | Только просмотр |
| `/lead UUID` | Показать статус и сводку заявки | Только просмотр; нужен полный UUID |
| `/pending` | Список заявок без подтверждённой доставки (`not_sent`, `sending`, `uncertain`) | Только просмотр; для `sending` повтор блокируется до проверки |
| `/retry UUID` | Повторно отправить уведомление оператору | Разрешено для `not_sent` и `uncertain`. Запрещено для `sent` и `sending`. Атомарно переводит заявку в `sending`, затем фиксирует `sent` или `uncertain`. **Может создать дубликат уведомления**, если предыдущая доставка на самом деле прошла |
| `/mark_sent UUID` | Вручную подтвердить доставку для заявки в `sending` | Только `submitted` + `sending`. Переводит в `sent`, пишет `manually_confirmed` и `manual_mark_sent`. Новое Telegram-сообщение **не** отправляется |
| `/reset_delivery UUID` | Подготовить безопасный сброс `sending` → `uncertain` | Только `submitted` + `sending`. Показывает кнопки с одноразовым токеном. Само подтверждение не шлёт уведомление; после сброса повтор делается отдельно через `/retry` |

#### Опасность повторной отправки

Если статус доставки **неизвестен** (`sending` после сбоя или `uncertain` после неподтверждённой отправки), Telegram **мог уже доставить** уведомление. Команда `/retry` отправляет сообщение ещё раз и может создать **дубликат** заявки у оператора.

Рекомендуемый порядок для застрявшей `sending`:

1. Проверить, приходило ли уведомление оператору.
2. Если доставка точно была — `/mark_sent UUID`.
3. Если доставка не подтверждена — `/reset_delivery UUID`, подтвердить кнопкой, затем при необходимости `/retry UUID`.

## Состояния доставки

Принятие заявки (`submitted`) и доставка уведомления (`delivery_status`) учитываются отдельно.

| Статус | Значение |
|---|---|
| `not_sent` | Заявка принята, отправка ещё не началась |
| `sending` | Отправка начата; результат ещё не зафиксирован |
| `sent` | Доставка подтверждена (Telegram или вручную через `/mark_sent`) |
| `uncertain` | Доставка не подтверждена; нужна проверка оператора |

### Типовые переходы

```text
accepted (submitted, not_sent)
        |
        v
     sending  ----успешная отправка----> sent
        |
        +---- сбой / таймаут ---------> uncertain
        |
        +---- /mark_sent -------------> sent
        |
        +---- /reset_delivery --------> uncertain
                                              |
                                              +---- /retry ----> sending ...
```

При временной сетевой ошибке во время первичной отправки предусмотрена **одна** автоматическая повторная попытка (`retrying` в журнале). Для ручного восстановления используются `/pending`, `/mark_sent`, `/reset_delivery` и `/retry`.

Каждый новый переход в `sending` получает новый `delivery_cycle_id`. Событие `retrying` внутри уже начатой отправки цикл не меняет.

## Подтверждение `/reset_delivery`

Команда не меняет заявку сразу. Она создаёт запись в `delivery_reset_confirmations` и отправляет оператору кнопки с одноразовым токеном в `callback_data`.

Защиты:

- криптографически случайный токен, укладывающийся в лимит Telegram `callback_data` (64 байта);
- срок действия **300 секунд** (5 минут);
- токен привязан к `lead_id`, `operator_id` и текущему `delivery_cycle_id`;
- подтверждение и отмена выполняются атомарно (`BEGIN IMMEDIATE`);
- повторное использование, отмена, просрочка, чужой оператор, поддельный токен или смена цикла доставки **не** изменяют заявку;
- при успешном подтверждении заявка переводится в `uncertain`, токен помечается использованным, пишутся `manually_reset` и `manual_reset_delivery`.

Отмена кнопкой аннулирует только токен и не меняет статус заявки.

## Журналы SQLite

### `delivery_attempts`

История событий доставки по заявке. Типичные значения `status`:

| Событие | Когда появляется |
|---|---|
| `accepted` | Заявка принята (`not_sent`) |
| `sending` | Начата первичная отправка |
| `retrying` | Автоповтор сети или резервирование `/retry` |
| `sent` | Telegram подтвердил отправку |
| `uncertain` | Доставка не подтверждена |
| `manually_confirmed` | Оператор выполнил `/mark_sent` |
| `manually_reset` | Оператор подтвердил `/reset_delivery` |

### `operator_actions`

Аудит действий оператора. Примеры:

| `action` | Команда / событие |
|---|---|
| `retry_sent` | Успешный `/retry` |
| `manual_mark_sent` | `/mark_sent` |
| `manual_reset_delivery` | подтверждённый `/reset_delivery` |

### `delivery_reset_confirmations`

Одноразовые токены сброса: срок действия, оператор, цикл доставки, признаки использования и отмены.

## Резервное копирование и восстановление

Автоматическое резервное копирование **не реализовано**. Ниже — ручные операции для текущего Docker Compose.

### Копия SQLite из volume

Контейнер должен быть остановлен или хотя бы не писать в БД во время копирования:

```powershell
docker compose stop ai-lead-assistant

New-Item -ItemType Directory -Force backups | Out-Null

docker run --rm `
  -v ai-lead-assistant_ai_lead_data:/data `
  -v "${PWD}/backups:/backup" `
  alpine `
  cp /data/sessions.db "/backup/sessions-$(Get-Date -Format yyyyMMdd-HHmmss).db"

docker compose start ai-lead-assistant
```

Имя volume уточняйте через `docker volume ls`, если префикс проекта отличается.

### Восстановление файла БД

```powershell
docker compose stop ai-lead-assistant

docker run --rm `
  -v ai-lead-assistant_ai_lead_data:/data `
  -v "${PWD}/backups:/backup" `
  alpine `
  cp /backup/sessions-YYYYMMDD-HHMMSS.db /data/sessions.db

docker compose start ai-lead-assistant
```

### Обновление образа без потери данных

```powershell
docker compose up -d --build
```

Volume `ai_lead_data` сохраняется при обычном `down`/`up` и пересборке образа. Данные теряются при `docker compose down -v` или ручном удалении volume.

### Безопасная проверка `/reset_delivery` на искусственной заявке

Скрипт `scripts/test_reset_delivery_live.py` создаёт отдельную тестовую заявку с именем `TEST RESET DELIVERY` и отрицательным `user_id`, **не** пересекающимся с реальными Telegram ID. Telegram-уведомления скрипт **не** отправляет.

Порядок:

```powershell
# создать тестовую заявку в sending (на той же БД, что использует бот)
docker compose run --rm --no-deps `
  -v "${PWD}/scripts:/app/scripts:ro" `
  ai-lead-assistant `
  python scripts/test_reset_delivery_live.py create

# в личном чате оператора с ботом:
# /reset_delivery <UUID из вывода / файла data/reset_delivery_test_id.txt>
# подтвердить кнопкой

docker compose run --rm --no-deps `
  -v "${PWD}/scripts:/app/scripts:ro" `
  ai-lead-assistant `
  python scripts/test_reset_delivery_live.py verify

docker compose run --rm --no-deps `
  -v "${PWD}/scripts:/app/scripts:ro" `
  ai-lead-assistant `
  python scripts/test_reset_delivery_live.py cleanup
```

Скрипт отказывается продолжать, если UUID-файл уже есть, тестовая заявка/сессия заняты или метки тестовой заявки не совпадают. `cleanup` удаляет только записи этой тестовой заявки.

## Ограничения MVP и планы

Уже реализовано относительно более ранних планов:

- ручная обработка заявок в `sending` через `/mark_sent` и `/reset_delivery`;
- одноразовые токены подтверждения сброса с привязкой к циклу доставки;
- диагностический скрипт для проверки сброса на искусственной заявке.

Остаётся ограничением MVP:

- улучшение последовательности уточняющих вопросов: бот всё ещё может одновременно запросить дополнительные сведения и предложить подтверждение;
- более надёжное сохранение Telegram ID клиента как контакта для последующей связи;
- отсутствие автоматического мониторинга доступности и автоматических бэкапов;
- отсутствие веб-интерфейса, CRM-интеграций и облачного развёртывания;
- нет автоматического «размораживания» `sending` без участия оператора.

## Безопасность

- Действующие API-ключи и токены храните только в `.env` или защищённом хранилище секретов.
- База заявок и runtime-данные исключены из Git (`data/`, `*.db`).
- Не публикуйте логи с токенами или персональными данными клиентов.
- Токены `/reset_delivery` не должны попадать в журналы приложения.
- Перед публичной эксплуатацией проверьте актуальность токена Telegram и ограничьте подробное логирование HTTP-запросов.

## Статус

**Работающий MVP для демонстрации и дальнейшей разработки.** Основной пользовательский сценарий и операторские команды восстановления доставки реализованы; проект не заявляется как production-ready сервис.
